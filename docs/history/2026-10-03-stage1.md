## Stage 1: Characterizing the Baseline

### Baseline Solver

The baseline `solver.c` implements an optimal solver for the 2×2×2 Mini-Rubik's Cube. One corner is fixed to remove whole-cube rotational symmetry, leaving 3,674,160 reachable states.

The solver performs a retrograde breadth-first search (BFS) starting from the solved state. Since every move in the half-turn metric (HTM) has unit cost, the first time BFS reaches a state is through a shortest path.

When BFS discovers a new state, it stores the inverse of the move used to reach that state. Therefore, the stored move always leads one step toward the solved state.

After the complete table has been constructed, solving a query only requires repeatedly looking up the stored move, applying it to the current state, and continuing until the state rank becomes zero.

The exhaustive BFS confirms that all 3,674,160 states are reachable and that the maximum shortest-path distance from any state to the solved state is 11 moves in HTM.

### State Representation and Invariants

A cube state is represented by two arrays of seven elements:

- `p[7]`: the permutation of the seven movable corner cubies.
- `o[7]`: the orientation of those cubies, where each orientation is represented by a value in `{0, 1, 2}`.
- For a valid state, the seven entries of `p[7]` must form a bijection of `{0, 1, 2, 3, 4, 5, 6}`. In other words, every movable cubie appears exactly once and no cubie is duplicated or missing.

Because one corner is fixed, the remaining seven corner cubies can be permuted in

$$
7! = 5040
$$

different ways.

Corner orientations satisfy the invariant

$$
\sum_{i=0}^{6} o_i \equiv 0 \pmod 3.
$$

Therefore, the orientation of the seventh cubie is uniquely determined by the first six. The number of possible orientation states is

$$
3^6 = 729.
$$

The total number of reachable states is therefore

$$
7! \times 3^6
= 5040 \times 729
= 3,674,160.
$$

The baseline solver maps each valid cube state to a dense integer rank. The permutation is encoded as a permutation rank `p`, while the first six orientations are encoded as a base-3 orientation rank `o`.

The final state rank is

$$
\text{rank} = p \times 729 + o.
$$

This encoding provides a one-to-one mapping between valid cube states and integer indices in the range from 0 to 3,674,159, allowing each state to be used directly as an array index.

### State Space as a Cayley Graph

Fixing one corner removes whole-cube rotational symmetry. The remaining reachable states form the fixed-corner group generated by the three face turns `R`, `B`, and `D`, written as `⟨R, B, D⟩`.

The order of this group is:

`7! × 3^6 = 3,674,160`

Each group element corresponds to one valid cube state.

The solver can therefore be interpreted as operating on a Cayley graph. Each of the 3,674,160 cube states is a vertex, and an edge connects two states when one legal HTM move transforms one into the other.

Although the group is generated by `R`, `B`, and `D`, the search uses nine HTM moves:

`R, R2, R', B, B2, B', D, D2, D'`

Each of these moves has unit cost in the half-turn metric.

Because all edges have equal cost, breadth-first search visits states in nondecreasing shortest-path distance from the solved state. Therefore, the first visit to a state determines its exact shortest distance from solved.

The exhaustive BFS reaches all `3,674,160` valid states and finds states at depth 11. The existence of depth-11 states establishes that the diameter cannot be smaller than 11. Since every valid state is reached and none occurs beyond depth 11, the diameter cannot be larger than 11. Thus, the HTM diameter is exactly 11.

Since a Cayley graph is vertex-transitive, measuring the maximum shortest distance from the identity element (the solved state) is sufficient to determine the diameter of the entire graph.

The orientation constraint is a modulo-3 invariant rather than a parity constraint. The seven corner orientations cannot be chosen independently: their sum must be congruent to zero modulo 3. Therefore, once the first six orientations are known, the seventh is uniquely determined. Configurations whose orientation sum is 1 or 2 modulo 3 are excluded from the reachable state space.

### Baseline Memory and Computational Cost

The baseline solver is efficient on a native host, but its resource requirements are unsuitable for direct execution in Ripes.

Its three dominant memory allocations are:

| Structure | Size |
| --- | ---: |
| One move toward solved for every state | 3,674,160 bytes |
| BFS queue of 32-bit state ranks | 14,696,640 bytes |
| Factored permutation/orientation transition tables | 34,614 bytes |
| **Total peak** | **18,405,414 bytes (17.553 MiB)** |

The BFS queue alone accounts for approximately 79.8% of the peak memory usage.

The complete BFS expands all 3,674,160 reachable states. Each state has nine legal HTM moves:

$$
R,\ R2,\ R',\ B,\ B2,\ B',\ D,\ D2,\ D'.
$$

Therefore, the total number of edge expansions is

$$
3,674,160 \times 9
= 33,067,440.
$$

For every candidate edge examined during BFS, the solver advances both the permutation component and the orientation component using the precomputed transition tables. Therefore, the complete BFS performs

$$
33,067,440 \times 2
= 66,134,880
$$

component-transition applications.

These costs are acceptable on a native machine, but the Ripes target changes the constraints significantly. The final RV32I implementation must keep the total static data within 128 KiB, so neither the complete BFS queue nor the full move-per-state table can be carried directly to the target.

This means that the main problem is not simply translating the baseline solver into RV32I assembly. The state representation and search strategy must first be redesigned to fit the target's memory and execution constraints.

### Ripes Environment

The measurements were performed using Ripes `v2.2.6-106-g5b8a616`.

The host-memory measurement used the `RV32_ISS` processor model. The simulation-rate measurement used both `RV32_ISS` and the pipelined `RV32_5S` model.

Ripes was executed using the Windows build through PowerShell, while the source repository and native C development environment use Ubuntu 24.04 LTS on WSL.

Because Ripes represents written guest memory using sparse host-side storage, the host memory cost of one guest byte is much larger than one byte. Therefore, the guest-memory overhead was measured empirically on this specific Ripes build instead of assuming a fixed ratio.

### Host Bytes per Guest Byte

To estimate the host-memory cost of guest memory in Ripes, two RV32I assembly programs were used.

The small control writes 64 KiB of guest memory, while the large case writes 4 MiB. Both programs use the same loop structure and differ only in the number of 32-bit stores.

Each case was executed five times using `RV32_ISS`. Peak working-set memory was sampled from the Ripes process, and the median peak was used.

During each run, PowerShell polled the Ripes process every 10 ms and recorded `PeakWorkingSet64`; the median of five peak values was used for each case.

| Run | Small Peak (MiB) | Large Peak (MiB) |
| ---: | ---: | ---: |
| 1 | 28.89 | 344.57 |
| 2 | 28.97 | 344.53 |
| 3 | 29.99 | 344.64 |
| 4 | 28.48 | 344.59 |
| 5 | 28.43 | 344.52 |

The median values were:

- Small peak: `30,289,920` bytes
- Large peak: `361,304,064` bytes
- Host-memory difference: `331,014,144` bytes
- Guest-memory difference: `4,128,768` bytes

The measured memory-expansion ratio is:

`331,014,144 / 4,128,768 ≈ 80.17`

Therefore, on this Ripes build, each additional written guest byte increases the host peak working set by approximately **80.17 bytes**.

Using this measured slope, the baseline peak guest-memory footprint of `18,405,414` bytes would correspond to roughly **1.4 GiB of host memory** under the same linear approximation.

This value is a projection rather than a direct measurement of the baseline itself. Nevertheless, it shows why the baseline full-table design is impractical for the Ripes target and motivates a different representation and search strategy.

### Retired Instructions per Second

To characterize the simulation speed of the target environment, a simple RV32I memory loop was executed using both the `RV32_ISS` processor and the pipelined `RV32_5S` processor.

The benchmark repeatedly stores a word to the same guest-memory address and decrements a loop counter. Reusing the same address prevents the benchmark from allocating a large sparse guest-memory region.

Each execution retired exactly `3,000,007` instructions. Ripes' `--iret` option was used to obtain the retired-instruction count, while `--exectime` reported the wall-clock model execution time.

After validating the measurement script, the formal measurement was repeated five times for each processor model.

| Run | RV32_ISS Time (ms) | RV32_ISS (instr/s) | RV32_5S Time (ms) | RV32_5S (instr/s) |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 102 | 29,411,833 | 9,640 | 311,204 |
| 2 | 103 | 29,126,282 | 9,662 | 310,495 |
| 3 | 102 | 29,411,833 | 9,686 | 309,726 |
| 4 | 102 | 29,411,833 | 9,758 | 307,441 |
| 5 | 103 | 29,126,282 | 9,822 | 305,437 |

The median simulation rates were:

- `RV32_ISS`: **29,411,833 retired instructions/s**
- `RV32_5S`: **309,726 retired instructions/s**

For this benchmark, `RV32_ISS` was approximately 95 times faster than the five-stage pipeline model.

This large difference makes `RV32_ISS` the practical choice for repeated performance measurements, while `RV32_5S` is more appropriate for visual pipeline inspection and instruction-level walkthroughs.

These measured rates are specific to the machine and Ripes build used in this assignment and should not be treated as fixed properties of Ripes.
