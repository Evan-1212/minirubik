## Stage 1: Characterizing the Baseline

### Baseline Solver

The baseline `solver.c` implements an optimal solver for the 2×2×2 Mini-Rubik's Cube. One corner is fixed to remove whole-cube rotational symmetry, leaving 3,674,160 reachable states.

The solver performs a retrograde breadth-first search (BFS) starting from the solved state. Since every move in the half-turn metric (HTM) has unit cost, the first time BFS reaches a state is through a shortest path.

When BFS discovers a new state, it stores the inverse of the move used to reach that state. Therefore, the stored move always leads one step toward the solved state.

After the complete table has been constructed, solving a query only requires repeatedly looking up the stored move, applying it to the current state, and continuing until the state rank becomes zero.

The exhaustive BFS confirms that all 3,674,160 states are reachable and that the maximum shortest-path distance from any state to the solved state is 11 moves in HTM.

### State Representation and Invariants

A cube state is represented by two arrays of seven elements:

- `p[7]`: the permutation of the seven movable corner cubies.
- `o[7]`: the orientation of those cubies, where each orientation is represented by a value in `{0, 1, 2}`.
- For a valid state, the seven entries of `p[7]` must form a bijection of `{0, 1, 2, 3, 4, 5, 6}`. In other words, every movable cubie appears exactly once and no cubie is duplicated or missing.

Because one corner is fixed, the remaining seven corner cubies can be permuted in

$$
7! = 5040
$$

different ways.

Corner orientations satisfy the invariant

$$
\sum_{i=0}^{6} o_i \equiv 0 \pmod 3.
$$

Therefore, the orientation of the seventh cubie is uniquely determined by the first six. The number of possible orientation states is

$$
3^6 = 729.
$$

The total number of reachable states is therefore

$$
7! \times 3^6
= 5040 \times 729
= 3,674,160.
$$

The baseline solver maps each valid cube state to a dense integer rank. The permutation is encoded as a permutation rank `p`, while the first six orientations are encoded as a base-3 orientation rank `o`.

The final state rank is

$$
\text{rank} = p \times 729 + o.
$$

This encoding provides a one-to-one mapping between valid cube states and integer indices in the range from 0 to 3,674,159, allowing each state to be used directly as an array index.

### State Space as a Cayley Graph

Fixing one corner removes whole-cube rotational symmetry. The remaining reachable states form the fixed-corner group generated by the three face turns `R`, `B`, and `D`, written as `⟨R, B, D⟩`.

The order of this group is:

`7! × 3^6 = 3,674,160`

Each group element corresponds to one valid cube state.

The solver can therefore be interpreted as operating on a Cayley graph. Each of the 3,674,160 cube states is a vertex, and an edge connects two states when one legal HTM move transforms one into the other.

Although the group is generated by `R`, `B`, and `D`, the search uses nine HTM moves:

`R, R2, R', B, B2, B', D, D2, D'`

Each of these moves has unit cost in the half-turn metric.

Because all edges have equal cost, breadth-first search visits states in nondecreasing shortest-path distance from the solved state. Therefore, the first visit to a state determines its exact shortest distance from solved.

The exhaustive BFS reaches all `3,674,160` valid states and finds states at depth 11. The existence of depth-11 states establishes that the diameter cannot be smaller than 11. Since every valid state is reached and none occurs beyond depth 11, the diameter cannot be larger than 11. Thus, the HTM diameter is exactly 11.

Since a Cayley graph is vertex-transitive, measuring the maximum shortest distance from the identity element (the solved state) is sufficient to determine the diameter of the entire graph.

The orientation constraint is a modulo-3 invariant rather than a parity constraint. The seven corner orientations cannot be chosen independently: their sum must be congruent to zero modulo 3. Therefore, once the first six orientations are known, the seventh is uniquely determined. Configurations whose orientation sum is 1 or 2 modulo 3 are excluded from the reachable state space.

### Baseline Memory and Computational Cost

The baseline solver is efficient on a native host, but its resource requirements are unsuitable for direct execution in Ripes.

Its three dominant memory allocations are:

| Structure | Size |
| --- | ---: |
| One move toward solved for every state | 3,674,160 bytes |
| BFS queue of 32-bit state ranks | 14,696,640 bytes |
| Factored permutation/orientation transition tables | 34,614 bytes |
| **Total peak** | **18,405,414 bytes (17.553 MiB)** |

The BFS queue alone accounts for approximately 79.8% of the peak memory usage.

The complete BFS expands all 3,674,160 reachable states. Each state has nine legal HTM moves:

$$
R,\ R2,\ R',\ B,\ B2,\ B',\ D,\ D2,\ D'.
$$

Therefore, the total number of edge expansions is

$$
3,674,160 \times 9
= 33,067,440.
$$

For every candidate edge examined during BFS, the solver advances both the permutation component and the orientation component using the precomputed transition tables. Therefore, the complete BFS performs

$$
33,067,440 \times 2
= 66,134,880
$$

component-transition applications.

These costs are acceptable on a native machine, but the Ripes target changes the constraints significantly. The final RV32I implementation must keep the total static data within 128 KiB, so neither the complete BFS queue nor the full move-per-state table can be carried directly to the target.

This means that the main problem is not simply translating the baseline solver into RV32I assembly. The state representation and search strategy must first be redesigned to fit the target's memory and execution constraints.

### Ripes Environment

The measurements were performed using Ripes `v2.2.6-106-g5b8a616`.

The host-memory measurement used the `RV32_ISS` processor model. The simulation-rate measurement used both `RV32_ISS` and the pipelined `RV32_5S` model.

Ripes was executed using the Windows build through PowerShell, while the source repository and native C development environment use Ubuntu 24.04 LTS on WSL.

Because Ripes represents written guest memory using sparse host-side storage, the host memory cost of one guest byte is much larger than one byte. Therefore, the guest-memory overhead was measured empirically on this specific Ripes build instead of assuming a fixed ratio.

### Host Bytes per Guest Byte

To estimate the host-memory cost of guest memory in Ripes, two RV32I assembly programs were used.

The small control writes 64 KiB of guest memory, while the large case writes 4 MiB. Both programs use the same loop structure and differ only in the number of 32-bit stores.

Each case was executed five times using `RV32_ISS`. Peak working-set memory was sampled from the Ripes process, and the median peak was used.

During each run, PowerShell polled the Ripes process every 10 ms and recorded `PeakWorkingSet64`; the median of five peak values was used for each case.

| Run | Small Peak (MiB) | Large Peak (MiB) |
| ---: | ---: | ---: |
| 1 | 28.89 | 344.57 |
| 2 | 28.97 | 344.53 |
| 3 | 29.99 | 344.64 |
| 4 | 28.48 | 344.59 |
| 5 | 28.43 | 344.52 |

The median values were:

- Small peak: `30,289,920` bytes
- Large peak: `361,304,064` bytes
- Host-memory difference: `331,014,144` bytes
- Guest-memory difference: `4,128,768` bytes

The measured memory-expansion ratio is:

`331,014,144 / 4,128,768 ≈ 80.17`

Therefore, on this Ripes build, each additional written guest byte increases the host peak working set by approximately **80.17 bytes**.

Using this measured slope, the baseline peak guest-memory footprint of `18,405,414` bytes would correspond to roughly **1.4 GiB of host memory** under the same linear approximation.

This value is a projection rather than a direct measurement of the baseline itself. Nevertheless, it shows why the baseline full-table design is impractical for the Ripes target and motivates a different representation and search strategy.

## Stage 2: State Representation and Solver Design

The baseline builds a complete move-to-solved table using breadth-first search (BFS). Its main allocations total 18,405,414 bytes: a 14,696,640-byte queue, a 3,674,160-byte move table, and 34,614 bytes of transition tables. This exceeds the assignment's 128 KiB static-data budget and requires full-state enumeration before answering a query.

The two C candidates replace this full-state enumeration with iterative-deepening A* (IDA*) over compact coordinates. Transition tables and abstract distance tables are generated on the host in C; the solver searches for a shortest solution at runtime. Version 1 (`optimized/`) uses separate permutation and orientation bounds. Version 2 (`optimized_v2/`) retains the search structure and adds a stronger mixed pattern database (PDB).

### State Representation

The baseline represents a cube using two seven-element arrays: one for corner permutation and one for corner orientation. Both candidates replace these arrays in the search state with two integer coordinates. This preserves the state information while reducing storage per state and allowing direct indexing into lookup tables.

#### Input format and validity

The solver preserves the baseline's 14-character input format. The front-upper-left corner is fixed, so the input describes the remaining seven corners.

| Input positions | Meaning | Accepted characters | Internal values |
| --- | --- | --- | --- |
| `0–6` | Cubie occupying each position | `'1'–'7'`, without duplicates | `0–6` |
| `7–13` | Orientation of the cubie at each position | `'1'–'3'` | `0–2` |

Permutation and orientation are both indexed by **position**. An orientation value describes the cubie currently occupying that position; it is not a color label.

In `v1_parse()`, the parser subtracts `'1'` from each character. A seven-bit mask detects repeated cubie labels. The parser also checks the orientation range and requires the string to end immediately after its fourteenth character. Version 2 reuses this parser.

A valid orientation assignment must satisfy:

$$
\sum_{i=0}^{6} o_i \equiv 0 \pmod{3}.
$$

Consequently, the seventh orientation is determined by the first six. For example, if their sum is 5, the seventh internal orientation must be 1. The parser checks the total-sum constraint using repeated subtraction of 3.

#### Permutation coordinate

There are $7! = 5040$ possible permutations. Each permutation is assigned a unique rank from 0 to 5039.

For position $i$, `smaller_after()` counts the smaller cubie labels appearing to its right. Calling this count $c_i$, the rank is:

$$
p = c_0 \times 6! + c_1 \times 5! + c_2 \times 4! + c_3 \times 3! + c_4 \times 2! + c_5 \times 1!.
$$

The last position contributes zero because nothing appears to its right. The implementation evaluates the expression incrementally, using multipliers 6, 5, 4, 3, and 2, expressed as shifts and additions.

For example, input permutation `2134567` becomes `{1, 0, 2, 3, 4, 5, 6}` internally. Only $c_0$ is nonzero, so its rank is $6! = 720$. The solved permutation has rank 0.

#### Orientation coordinate

The first six internal orientations are encoded as a base-3 integer:

$$
o = o_0 \times 3^5 + o_1 \times 3^4 + o_2 \times 3^3 + o_3 \times 3^2 + o_4 \times 3 + o_5.
$$

This gives $3^6 = 729$ possible coordinates, numbered from 0 to 728. The parser accumulates the coordinate with the equivalent operation `o = 3 * o + digit`, implemented using a shift and additions. Although only six values are encoded explicitly, the coordinate represents all seven orientations because of the sum constraint.

Together, the coordinates uniquely represent:

$$
5040 \times 729 = 3{,}674{,}160
$$

valid states.

#### Stored state and solved-state condition

The coordinate structure in `optimized/v1.h` is shared by both candidates:

```c
typedef struct {
    uint16_t p, o;
} v1_coord;
```

The fields occupy 4 bytes, compared with the baseline's 14 bytes of array elements. This concerns the state fields only; structure padding, lookup tables, and search workspace must be accounted for separately.

| Input | Permutation coordinate | Orientation coordinate |
| --- | ---: | ---: |
| `12345671111111` | 0 | 0 |
| `21345671111111` | 720 | 0 |
| `12345672221111` | 0 | 351 |

The cube is solved only when **both coordinates are zero**:

```c
p == 0 && o == 0
```

A zero permutation coordinate alone means that all cubies occupy their correct positions, but their orientations may still be incorrect.

### Move Tables and Version 1 Heuristic

Both candidates use the nine moves `R`, `R2`, `R'`, `B`, `B2`, `B'`, `D`, `D2`, and `D'`. Under the half-turn metric (HTM), each costs one move, including a half turn.

A move updates the permutation independently of orientation. In this model, the orientation update also depends only on the previous orientation vector and the face being turned. Two quarter-turn tables therefore suffice:

```c
next.p = v1_perm_next[face][current.p];
next.o = v1_ori_next[face][current.o];
```

Applying the same face transition once, twice, or three times produces its three candidate moves. The search advances a saved cursor successively to generate `R`, `R2`, and `R'`. These are **siblings at the same search depth**, each one HTM move from the parent. Generating all three uses three transition-table pairs, rather than restarting from the parent and using $1+2+3$ pairs.

Version 1 uses two exact abstract distances:

| Table | Goal required by the abstraction |
| --- | --- |
| `v1_perm_dist[p]` | All cubies in their correct positions; orientations unrestricted |
| `v1_ori_dist[o]` | All orientations correct; cubie permutation unrestricted |

The host generator builds each distance table by BFS from its abstract goal, considering all nine unit-cost moves. The first visit gives the shortest abstract distance. Since every move has an inverse of equal cost, distances outward from the goal are also distances back to the goal.

The heuristic is:

$$
h_1(p,o) = \max\bigl(d_p(p), d_o(o)\bigr).
$$

Any complete solution must satisfy both abstract goals, so each distance is a lower bound on the complete solution length. Their maximum remains a lower bound. Adding them would not generally be valid because one move can improve both components.

### Iterative Search, Pruning, and Replay

The solver starts with `bound = h(start)` and performs a depth-first search within that threshold. For a generated child at depth $g$, it prunes when:

$$
g + h(\text{child}) > \text{bound}.
$$

The implementation first checks that `child_depth` does not exceed `bound`, then compares the heuristic with `bound - child_depth`. This ordering avoids unsigned subtraction underflow.

If a complete iteration finds no solution, these implementations increase `bound` by one, up to 11. This is the threshold policy used here; it is not a requirement that all IDA* implementations increase thresholds by one. A solved input returns length 0.

#### Same-face pruning and optimality

After turning one face, the next move cannot use that same face. Two consecutive turns of one face either cancel or combine into a single HTM move. A shortest solution therefore never needs such a pair. This leaves nine choices at the root and six at subsequent expanded states, before heuristic pruning.

Let the true shortest solution length be $D$. Along a shortest path, admissibility gives $g+h \leq D$. Thus, when the threshold reaches $D$, heuristic pruning cannot remove that path, and same-face pruning cannot remove all shortest paths. Thresholds from `h(start)` through $D-1$ have already been exhausted; lengths below `h(start)` are excluded by the lower bound itself. The first returned solution therefore has minimum length. The upper bound of 11 covers the legal fixed-corner state space under this move metric.

#### Explicit search frames

Both candidates use an explicit array instead of recursive calls:

```c
typedef struct {
    uint16_t p, o, cursor_p, cursor_o;
    uint8_t face, turn, previous_face;
} frame;

static frame frames[V1_MAX_DEPTH + 1];
```

Each frame stores the state at that depth, the cursor used to generate candidates, and the progress needed to resume after returning from a child. The parent advances its `turn` field before descent. On backtracking, its frame still identifies the next candidate to try. When a new branch enters the same depth, it overwrites that depth's previous frame.

Only the current path is retained. The number of frames depends on the maximum depth, not on how many candidates have been examined. The array has 12 entries; the recorded native build uses 12 bytes per frame, including padding, for 144 bytes total. This is search-frame storage, not the solver's total memory. The static workspace also makes these solver functions non-reentrant.

#### Solution path and replay

The caller supplies an 11-byte path buffer. Move codes `0–8` represent the nine moves in the order listed above. `path[depth]` records the move chosen at that depth and may be overwritten while exploring a different branch.

On success, the solver returns the solution length. `v1_replay()`, also reused by v2, applies only that many path entries and checks that both final coordinates are zero. Entries beyond the returned length are irrelevant. Replay establishes that the returned sequence solves the cube; the search argument above establishes shortest length. Multiple different shortest move sequences may exist.

### Version 2: Mixed Pattern Database

Version 2 retains the full search state `(p, o)` and the same transition tables and search structure. It changes the heuristic by tracking the positions of cubies **1, 2, and 7**, using input labels, together with the **complete orientation coordinate**. Their internal labels are `0`, `1`, and `6`.

The positions of these three distinct cubies have:

$$
7 \times 6 \times 5 = 210
$$

ordered placements. A host-generated projection maps every full permutation to a placement index `q`:

```c
unsigned q = pdb->projection[s.p];
```

The mixed abstract state is `(q, o)`. Its goal requires the selected cubies to occupy their correct positions and all seven orientations to be correct. The identities of the other four cubies are ignored by this abstraction, although the search still retains them in `p`.

Two full states share a mixed PDB entry when their selected-cubie positions and complete orientation coordinates are identical. Exchanging unselected cubie identities while preserving orientations at every position leaves that entry unchanged. Changing an unselected cubie's orientation can change the entry.

There are:

$$
210 \times 729 = 153{,}090
$$

abstract states. The host generator runs BFS from the mixed goal, using the same nine HTM moves. Its uncompressed logical index is `q * 729 + o`. The runtime heuristic becomes:

$$
h_2(p,o) = \max\bigl(d_p(p), d_m(q,o)\bigr).
$$

A complete solution projects to a valid mixed solution, so $d_m$ cannot exceed the complete solution distance. Moreover, the mixed goal includes the entire orientation goal, so $d_m(q,o) \geq d_o(o)$. Consequently, $h_2 \geq h_1$ for every state. There is no need for a separate orientation-distance lookup in v2.

#### Placement encoding and abstraction size

For the three selected cubies in a fixed label order, let `a`, `b`, and `c` be their distinct position indices in `0–6`. The host generator ranks their placement using:

```c
return (a * 6 + b - (a < b)) * 5 + c - (a < c) - (b < c);
```

In C, each comparison contributes either 0 or 1. Subtracting `(a < b)` removes the already-occupied position `a` from the numbering for the second cubie. The two subtractions involving `c` remove both previously occupied positions from the numbering for the third. The remaining choice counts are 7, 6, and 5, producing ranks `0–209` without gaps. This calculation runs during host generation; the solver obtains the rank through `projection[p]`.

For the selected input labels `1, 2, 7`, the solved positions are `a=0`, `b=1`, and `c=6`, giving `q=4`. Thus the mixed goal is `(q, o) = (4, 0)`, with uncompressed index `4 * 729 = 2916`. The complete cube's goal remains `(p, o) = (0, 0)`; the placement rank is a separate numbering scheme.

For any fixed `(q, o)`, the four unselected identities can occupy the remaining positions in $4! = 24$ ways. The abstraction therefore groups exactly 24 full states into each entry:

$$
\frac{3{,}674{,}160}{24} = 153{,}090.
$$

A face move maps selected positions to new positions and updates the orientation vector without consulting the omitted identities. Applying a move before projecting therefore gives the same abstract state as applying the corresponding abstract move after projecting. This makes the mixed transitions well-defined and supports the lower-bound argument above. The PDB stores abstract distances; the full-state search still has to resolve the remaining permutation.

#### Why select cubies 1, 2, and 7?

The host program `select_pattern.c` evaluates all $\binom{7}{3}=35$ subsets. Each uses the same abstraction size and is tested on all 2,644 distance-11 inputs, with solution-length and replay checks. Selection first minimizes the **maximum generated-child count** across those inputs, then the total count, then the cubie labels in lexicographic order. The maximum is prioritized because the assignment places a limit on every distance-11 case.

The stored host sweep illustrates why the objective matters:

| Input cubie labels | Maximum generated children | Total generated children |
| --- | ---: | ---: |
| 1, 2, 3 | 114,378 | 38,631,493 |
| **1, 2, 7** | **109,629** | **49,153,465** |
| 1, 4, 7 | 154,230 | 31,788,394 |

The selected subset has the lowest maximum among all 35 candidates, even though other subsets have smaller totals. These are recorded host search counts from `results/pattern_sweep.csv`, not target instruction counts. They justify this choice within the three-cubie family; they do not establish that it minimizes runtime or RV32I instructions. `pattern.txt` records the selected labels.

### Packing and Mixed-Distance Lookup

The table generator checks that distances do not exceed 11, so each fits in four bits. Version 2 stores two distances per byte: the even orientation index in the low nibble and the following odd index in the high nibble. Packing preserves the exact distance values.

Each placement has 729 orientation entries. Since 729 is odd, each row occupies:

$$
\left\lceil \frac{729}{2} \right\rceil = 365 \text{ bytes}.
$$

The final byte stores orientation index 728 in its low nibble. Its unused high nibble is padding with value 15. The whole packed distance array occupies $210 \times 365 = 76{,}650$ bytes, compared with 153,090 bytes at one byte per distance.

Packing every entry continuously across row boundaries could use 76,545 bytes. The implemented row layout spends an extra 105 bytes so that every row starts at a byte boundary and the nibble choice depends only on whether `o` is odd or even. The 840-byte `row_offset` table supplies each row's starting offset, avoiding a runtime multiplication by 365 in the accessor. These are explicit space-for-addressing tradeoffs; their instruction benefit must be checked on the target.

The accessor uses the following operations, with optional diagnostic counting omitted:

```c
unsigned q = pdb->projection[s.p];
unsigned offset = pdb->row_offset[q] + (s.o >> 1);
unsigned shift = (s.o & 1U) << 2;
return (pdb->packed[offset] >> shift) & 15U;
```

| Expression | Meaning |
| --- | --- |
| `row_offset[q]` | Starting byte of row `q`; the generator stores `q * 365` |
| `s.o >> 1` | Byte index within the row, equivalent to integer division by 2 |
| `(s.o & 1U) << 2` | Shift by 0 for an even index or 4 for an odd index |
| `& 15U` | Retain only the selected four-bit distance |

For example, `q = 1` and `o = 6` give `offset = 365 + 3 = 368`. The accessor reads the low nibble of `packed[368]`. The logical uncompressed index and the packed byte offset are different: each row has its own padding nibble.

During child pruning, v2 checks the cheaper permutation bound first:

```c
if (v1_perm_dist[next.p] > remaining ||
    v2_pattern_distance(pdb, next) > remaining) {
    /* Prune this child. */
}
```

If the left operand is true, C short-circuit evaluation skips the mixed lookup. This is equivalent to comparing the maximum of the two bounds with `remaining`. The initial-bound function still reads both distances to compute that maximum explicitly.

### Memory Budget and Design Choice

The table payloads follow directly from the array dimensions and element types:

| Table | Size calculation | v1 bytes | v2 bytes |
| --- | --- | ---: | ---: |
| Permutation transitions | `3 * 5040 * 2` | 30,240 | 30,240 |
| Orientation transitions | `3 * 729 * 2` | 4,374 | 4,374 |
| Permutation distances | `5040 * 1` | 5,040 | 5,040 |
| Orientation-only distances | `729 * 1` | 729 | — |
| Permutation-to-placement projection | `5040 * 1` | — | 5,040 |
| Row offsets | `210 * 4` | — | 840 |
| Packed mixed distances | `210 * 365` | — | 76,650 |
| **Total table payload** | | **40,383** | **122,184** |

The supplied v2 build uses function/data sections and linker garbage collection to discard unused v1 search code, v1 frames, and the orientation-only distance table. The v2 total above counts the tables used by its solver, not every array appearing anywhere in the shared source files.

The 128 KiB budget is 131,072 bytes. After table payload alone, v1 leaves 90,689 bytes and v2 leaves 8,888 bytes. These are remaining allowances, not final free-space measurements. Frames, the path buffer, pattern-view pointers, strings, alignment, and other linked static data must also fit. The final target must be checked using its actual `.data`, `.bss`, and `.rodata` sizes. Host BFS queues and verification oracles are outside the runtime solver and must not be linked into the target program.

| Design aspect | v1 | v2 |
| --- | --- | --- |
| Stored search state | Full `(p, o)` | Full `(p, o)` |
| Heuristic | Maximum of permutation and orientation distances | Maximum of permutation and mixed distances |
| Search and pruning | Iterative IDA* with same-face pruning | Same structure; mixed lookup skipped when permutation already fails |
| Main advantage | Smaller tables and simpler lookup | Stronger or equal lower bound |
| Main cost | A weaker bound can retain more candidates | Larger tables and extra lookup/unpacking work |

Version 2 is the provisional candidate for the RV32I port, with v1 retained as the smaller-memory reference. The stronger bound offers a way to reduce search work, but the benefit must be compared with its lookup cost. Packing reduces the mixed table's storage; it does not make v2 smaller than v1 overall.

Stage 3 will analyze operation costs and report the comparison evidence. Native elapsed time and search counters must be distinguished from Ripes retired instructions. Final acceptance still requires target memory checks and the instruction limit over all distance-11 inputs; the design alone does not establish either result.

### Initial native validation on WSL — 2026-10-04


The environment information and complete output are stored in [the WSL validation directory](https://github.com/Evan-1212/minirubik/tree/f4e8eee/measurements/2026-10-04-native-check).

| Check | Version 1 (`optimized/`) | Version 2 (`optimized_v2/`) |
| --- | --- | --- |
| Solved, one-move scramble, and distance-11 self-tests | PASS | PASS |
| CLI solution/replay tests and invalid-input rejection | PASS | PASS |
| H1: heuristic admissibility over all 3,674,160 states | PASS | PASS |
| H2: table completeness, maximum values, and solved entries | PASS | PASS |
| H4: packed accessors against an unpacked reference | Not applicable: unpacked byte tables | PASS |
| H3: exhaustive optimal-solution search on this WSL installation | Pending | Pending |

The full-state comparison also confirmed that Version 2's heuristic is never smaller than Version 1's, with strictly larger values for 3,189,950 states. This establishes a stronger lower bound, but does not by itself establish lower RV32I instruction counts.

Version 2's native binary contains 122,795 bytes of static data, including `.data.rel.ro`. This is a host-build result; the final RV32I section sizes and Ripes retired-instruction counts remain to be measured. Target correctness gates T5–T7 are also pending.

The C implementations and validation tools were developed with AI assistance. The checks reported in this subsection were executed locally on WSL. Earlier results bundled in `optimized/results/` and `optimized_v2/results/` come from a separate execution environment and are kept distinct from this local run.
